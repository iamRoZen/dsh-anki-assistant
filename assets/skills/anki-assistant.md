# Anki Assistant 制卡方法

这套方法解决一件事：**从资料到一张能背的卡**。工具只做确定性的事（存方案、排队、校验、写入、回读），
判断留给你。

## 一、先定尺度，再动手

| 请求长什么样 | 怎么做 |
|---|---|
| 改一张卡、查一个牌组、问一句概念 | 直接用 Anki 读写做完，**不要建任务、不要建批次** |
| 一批卡（一节、一章、一篇讲义） | 建批次：`batch open` → 逐题 `put` → `validate` → `card_write plan/commit` |
| 要留可检查的文档，或明天还要接着做 | 当项目推进：先把问题集与答案落成文件，再进批次 |

不要为了显得有条理而给单张卡套流程。

## 二、先看有没有现成方案

`scheme list` → 选中 `scheme get id=…`。

方案里写了五件你现在就要遵守的事：字段规范、各阶段做法、质量规则、验收标准、已知局限。
**没有合适方案时才新建**：`scheme save` 写一份 `status: draft`，说明为什么需要它；
经用户确认后再改成 `active`（`save` 会生成新版本，旧版本永远留着）。

## 三、取原文：按小节标题，不按概念词

在资料里找的是**回答题干的那一段**，入口是小节标题（`【诊断】`、`适应证`、`治疗原则`），
不是药名或病名这类概念词。

- 按概念词过滤会把别处的同类表述抓进来，拼出一段读起来像标准答案、但原文没有的东西。
- 取到之后立刻记定位：`materials path=… pages=…` 会返回 `p31:L14` 这样的行号，写进卡的定位字段。
- 定位写不出来，说明还没真正取到原文——停下来说明，不要凭印象写答案。

## 四、答案先成树，再压成句

1. **判根数**：把答案缩成顶层，是一个根还是两个互不依赖的根？两个就拆成两张卡。
2. **判形状**：原文是并列、分层，还是行列对照？照原文的编号走，不照好看的样子走。
3. **写骨架**：只有编号和分支名，一个内容词都不填。这一步能看出树是否真的建起来。
4. **填内容**：每个叶子一行，单行不超过 25 字。超了就是这行塞了两个判断。
5. **压缩**：删措辞，不删层级、限定语、方向、阈值。压完回读一遍，看还能不能顺着推下来。

六条平铺、每条都带主语，看着齐全，其实没有树——那是压缩时把层级压平了。

## 五、记忆提示是卡的一个字段

记忆提示（`role: memory` 的字段，通常是"笔记"或 `Extra`）回答的是**这张卡怎么背**：

- 回忆起点：看到问题先想起哪个词或哪个动作。
- 递推关系：第一条推第二条靠什么。
- 最容易漏的一步：哪一项考试最常丢。

它**不是**答案的复述，也不是卡组之外的讲解。写两行以内；写不下说明这张卡该拆。

## 六、写卡与校验

字段按方案来，不按手感来。规则引擎只查机械项（挖空包裹、长度、必填、禁用 Markdown），
语义对错由你对照原文逐条核：

- `batch validate` 会跑方案规则并查重（判重问 Anki，首字段相同即重复）。
- 写不进去先看 `card_write plan` 的 ✗ 行，那里写明了哪条规则、哪个字段。

## 七、样卡先行，再批量

批量写入前必须让用户看过预览：

1. 做 2–3 张样卡放进批次。
2. `card_write plan`，把预览给用户看。
3. 用户提意见 → 改字段或改方案（方案要改就 `scheme save` 出新版本，并在批次里换版本）。
4. 用户确认 → `card_write commit`。
5. `card_write verify` 回读，确认字段与计划一致。

批量写入是幂等的：提交前会先按标签把已经写过的卡找回来，再补写剩下的。中断了重跑 `commit` 即可，
不会重复出卡。

## 八、从一次操作沉淀方案

用户改卡时体现出新写法（比如答案改成表格、记忆提示固定写三步），不要直接改 active 方案：

1. `scheme save` 一份 `status: draft`，`changeWhy` 写清是哪次操作、改了什么。
2. 告诉用户这是候选。
3. 用户确认后再 `save` 成 `active`。

## 九、不要做的事

- 不替用户点评分、不改调度——那会往复习数据里灌假信号。
- 不猜字段：方案的字段要以 `modelFields` 实际结果为准，对不上就报错，不要静默写空。
- 不把定位写成"某章节"这类模糊说法；回查不到就等于没有依据。
- 删除只走用户明确要求；批量删除要先确认范围。
