# Anki Assistant：能力目录

这里只说明**有哪几种能力、每种能力处理什么对象、交付前至少要满足什么**。
用哪几种、按什么顺序、拆成几步、什么时候回查或停下，由所选方案决定——同一个能力在不同方案里做法可以完全不同。

## 五个能力

| 能力 | 处理的对象 | 交付物 | 最低质量要求 |
|---|---|---|---|
| **资料整理** | 一份具体资料（书、PDF、讲义、网页、已有笔记） | 可回读的定位 + 要用的原文片段 | 每条结论都能顺着定位回到原文；定位不到就说明，不拿印象顶替 |
| **问题集整理** | 学习目标 / 资料 / 题库 | 问题清单（题干、题型、来源、稳定 id） | 问题要问**原文与答案问的同一件事**；题干照抄不改写；自拟要标明 |
| **撰写答案** | 一道问题 + 对应原文 | 答案与逐条依据 | 答案正面回答这道题；每条有依据；原文没有的结论不写 |
| **制作卡片** | 问题 + 答案 + 卡片模板 | 符合模板字段的卡片，写入后回读 | 字段来自模板；判重键是首字段；写入后回读一致 |
| **制作记忆指导** | 答案结构 + 易错点 | 卡上的记忆提示 | 说清"怎么背"，不复述答案；写不下说明该拆 |

要点：

- 每个能力都能**单独用**。这次只要问题集，就跑「资料整理 + 问题集整理」；只要背诵路径，就跑「制作记忆指导」。
  这些是**这次任务交什么**，不是方案——方案库里只有卡型做法，没有用来交问题集的方案。
- 每个能力都能**跳过**。已有题干和带出处的答案，可以直接从制作卡片开始。
- 顺序不是固定的。资料整理可以从章节入手找概念关系，也可以从一道真题入手逐题找证据；
  答案可以在问题集之后批量写，也可以边出题边写。

## 方案 = 一种卡型的做法

方案库里每一条，回答的都是"**这种卡怎么做**"：字段规范、格式要求、检查标准、什么情况停。
所以方案总是绑定一个卡型（以及一种取材方法）：同一卡型可以有多套方案，取材路径不同。

这次交什么（问题集 / 答案文档 / 记忆指导 / 卡）由任务决定，不由方案决定。

## 对象要求 ≠ 呈现形式

- 对**对象**的要求是硬性的：题目要保留原选项与题源；答案要对应题目；引用要能回查。
- **形式**是选择：清单用表格还是列表、答案用序号树还是表格、记忆提示写几行。
  形式由用户要求、内容结构或方案决定，不写死在通用层。

## 先看方案

`scheme list` → `scheme get id=…`。返回三样东西：

- 方案正文（`body`）：这套方案用哪些能力、怎么拆步骤、什么情况回查、什么情况停、怎么验收；
- 卡片模板（`templateBody`，只有出卡方案才有）：模型、字段、卡面、格式约束；
- 用过的实践（`practices`）：真实跑过的记录。

没有合适方案再新建：`scheme save` 写 `status: draft`，说明为什么需要；确认后 `active`。
保存即新版本，旧版永久保留。

## 从实践和素材整理方案

方案是产出的副产品，不是开工前写的文档。顺序：

1. **素材**：读到的文章、博文、讲义，先原样记要点，不急着建方案。
2. **方法草稿**：确实想试，就 `scheme save` 只给 id、title、正文（`deliverable: "method"`），零结构。
3. **做几张真卡**：按草稿做 2–3 张，记下实际用了哪些规则、哪些没用上。
4. **沉淀**：真卡存进 `samples/`（一张能过、一张该被拦），用上的规则写回正文；能形式化的写进 `quality.rules` 或 `validate.mjs`。
5. **测试**：`scheme test id=…` 跑方案自带的 `test/run.mjs`，或用 `validate.mjs` 跑样本与反例；不通过不算完成。
6. **升级**：有真实产出、测试通过后，再补模型与字段，转成卡片方案并 `active`。

任务收尾时主动做一次判断：这次有没有值得复用的做法？有就存成 draft 并说明理由；没有就说明为什么不建。

没有产出的草稿不升级，也不假装是卡片方案；一次性的任务不值得建方案。

## 渲染、检查与呈现

- 遇到 `cloze:BRACE`：先用 `batch fix`（默认只报告，`apply=true` 才写回）把挖空内部的
  `}}` 改成 `} }`，再跑一次 `validate` 刷新 issues；同类修复也允许写进方案目录的 `scripts/`。
- 卡片写完或改完，用 `card_preview` 出预览（`png` / `split` / `pdf` 按需要），
  然后把文件**呈现给用户**（`present` 或给出路径），不要只说"已生成"。
- 验收分两层：**工程验收**看测试与检查是否通过；**用户验收**是给用户看真实卡的渲染图。
  每次改动后至少给一张真实卡的渲染图并 `present`；测试全绿不等于用户看过。
  Anki 没开时说明取不到，并用最近一次真实渲染代替，不要拿示意图冒充。
- 自检两层：`measure` 看横向溢出，`read_image` 看实际观感（断行、公式、表格）。
- 发现问题自己修：改字段 → 重新 `plan` / `commit` → 重新 `card_preview` →
  **呈现修正后的版本**，并说明改了什么。不要停在"发现了一个问题"。
- 只有修不动、或涉及设计取舍（例如要不要换方案风格）时才问用户。

## 工具只做确定性的事

`materials` 取原文与行号；`batch` 排队；`card_write` 预览/写入/回读；`practice` 看案例。
判断（选哪段原文、怎么拆、怎么写）由你按方案做。

写入前把 `card_write plan` 的预览给用户看；改了草稿、方案版本或目标，旧计划作废，要重新 plan。
